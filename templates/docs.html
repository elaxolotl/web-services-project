1. Overview

1.1 Introduction

The Gavel API is a transparency-focused RESTful API designed to modernize and manage the auctioning of detained goods in customs, specifically tailored for ports. It digitizes a traditionally manual and opaque process, introducing real-time visibility, secure bidding, and automated workflows to ensure fairness and efficiency.

1.2 Key Features

  • User Authentication & Roles: Supports signup/login via JWT with clearly defined roles: customs officers, bidders, and goods owners.
  • Goods Management: Add, edit, view, and delete detained goods with rich metadata (perishability, expiry date, category, etc.).
  • Auction System: Create auctions, place bids, and automatically assign winners using a scheduled task.
  • Bid Transparency: All bids are publicly visible to eligible users, encouraging higher and fairer offers.
  • Filtering & Sorting: Easily search and prioritize listings (e.g., by perishability or auction status).

2. Authentication & security

The Gavel API uses JWT-based authentication combined with role-based access control (RBAC) to ensure that all interactions are secure, permission-based, and auditable. Each user must authenticate before accessing protected routes, and their access is restricted based on their assigned role.

2.1 Authentication workflow

  • User signup
    • Endpoint: 
      POST /signup
    • New users must register with an email, password, name, and role ID.
    • Depending on the role, additional identifiers like national ID or fiscal ID may be required (for buyers only).
  • User login
    • Endpoint: 
      POST /login
    • Accepts email and password.
    • Returns a JWT token which must be included in all future requests to protected endpoints using the Authorization header: 
      Authorization: Bearer <your_jwt_token>
  • Token expiry
    • JWTs have a limited lifespan.
    • Expired or invalid tokens will be rejected with appropriate error messages.

2.2 Roles and access control

Access to Gavel API endpoints is restricted based on user roles. Each role has specific permissions that determine what actions the user can perform within the system.

Role Role ID Permissions
Customs Officer 1 Full control over detained goods, create/edit/delete goods, manage auctions
Buyer 2 View detained goods, place bids, view and delete own bids
Owner 3 View owned goods (future support)

Role-based access is enforced using decorators in the backend, ensuring that only users with the appropriate roles can access or modify protected resources.

2.3 Security Features

The Gavel API implements several modern security practices to protect user data, ensure system integrity, and enforce access control.

Password Security
  • Passwords are hashed using the pbkdf2:sha256 algorithm before being stored in the database.
  • Plaintext passwords are never saved or transmitted.
Token-Based Access
  • Authentication is handled using JSON Web Tokens (JWT).
  • Tokens are issued on successful login and must be included in the Authorization header for protected routes.
  • Expired or invalid tokens are automatically rejected.
Input Validation
  • All incoming requests are validated using strict Marshmallow schemas.
  • Examples: UserSignupSchema, UserLoginSchema, BidSchema.
  • Malformed or incomplete data is rejected before processing.
Role-Based Access Control
  • Each route has access restrictions enforced by role-specific decorators.
  • Only users with appropriate permissions can perform sensitive operations.
Session Security
  • User sessions are managed using JWTs combined with Flask-Security mechanisms.
  • This ensures secure interaction across multiple requests without storing session data server-side.

3. API Reference

3.1 User Management

  • User signup
    • Endpoint: 
      POST /signup
    • Registers a new user with email, password, name, and role ID.
    • Buyers (role_id = 2) must also provide national ID and fiscal ID.
  • User login
    • Endpoint: 
      POST /login
    • Accepts email and password and returns a JWT token.
    • The token must be included in protected requests via the Authorization header: 
      Authorization: Bearer <your_jwt_token>
  • Get user info
    • Endpoint: 
      GET /user
    • Returns the logged-in user's email and role.

3.2 Detained Goods Management

  • Create a detained good
    • Endpoint: 
      POST /goods
    • Customs officers can create a new detained good using this endpoint.
    • Requires a valid JWT and minimum fields: name, container_id, opening price, status, guarantee, perishable.
  • List all detained goods
    • Endpoint: 
      GET /goods
    • Returns a public list of all detained goods.
    • Results are prioritized by perishability and expiry/due dates.
  • View a specific detained good
    • Endpoint: 
      GET /goods/{goods_id}
    • Returns details of the detained good by ID. No authentication required.
  • Edit a detained good
    • Endpoint: 
      PUT /goods/{goods_id}
    • Allows customs officers to update goods' data. Requires a JWT token.
  • Delete a detained good
    • Endpoint: 
      DELETE /goods/{goods_id}
    • Allows customs officers to delete a good. Requires a JWT token.

3.3 Auction System

  • Create an auction
    • Endpoint: 
      POST /goods/{goods_id}/auctions
    • Customs officers can start an auction for a good. Requires JWT token.
  • Place a bid
    • Endpoint: 
      POST /goods/{goods_id}/bids
    • Buyers can place a bid on a good currently on sale. JWT required.
    • Bid value must be greater than the opening price.
  • List all bids for a good
    • Endpoint: 
      GET /goods/{goods_id}/bids
    • Returns all bids (highest to lowest) for a specific good. JWT required.
  • View a specific bid
    • Endpoint: 
      GET /bids/{bid_id}
    • Returns bid details by bid ID. JWT required.
  • Delete a bid
    • Endpoint: 
      DELETE /bids/{bid_id}
    • Buyers can delete their own bids. JWT required.

4 Filtering & Sorting

  • Goods listing priority
    • Endpoint: 
      GET /goods
    • All detained goods are returned in a prioritized order:
      • Perishable goods come first, sorted by expiry_date (earliest first).
      • Non-perishable goods follow, sorted by due_date.
  • Filtering by status
    • Endpoint: 
      GET /goods?status=on%20sale
    • You can filter goods based on their current status using the status query parameter.
    • Available statuses include:
      • detained
      • on sale
      • sold
      • no commercial value
